The 80/20 deterministic test fabric

Design alternatives to a full deterministic hypervisor: preserve most of the value—controlled inputs, fault exploration, invariant checking, and useful replay—without first solving whole-machine determinism.

Antithesis makes arbitrary systems deterministic from below. Living Dictionary can create systems that are testable from above, then execute each one in the least powerful machine sufficient to prove its claims.

Step back

Determinism is not the whole product

A full deterministic hypervisor is one way to obtain four separable benefits. LD already owns much of the control and validation plane, so it can buy the remaining benefits incrementally.

01

Controlled world

Constrain clocks, randomness, filesystems, networks, resource limits, and initial state.

02

Exploration

Run many seeded workloads, schedules, inputs, and faults—not merely the happy path.

03

Oracles

Continuously check properties and discharge claims. “The model stopped” is never success.

04

Replay

Retain enough initial state, seed, inputs, and fault events to reproduce or statistically recover failures.

A portfolio, not a bet

Use the cheapest machine that can discharge the claim

Treat determinism as an explicit capability budget. A parser does not need a deterministic Linux cluster; an existing distributed database cannot fit inside a pure Wasm component.

Target choices

Four practical product paths

These are complementary execution profiles sharing one claim and receipt protocol.

Recommended first

WASI deterministic machine

Compile generated programs to Wasm. Expose only deterministic imports; use fixed fuel and memory bounds.

  • Fast enough for large seed campaigns
  • Excellent capability boundary
  • Portable across developer and CI hosts
  • Easy memory snapshots and semantic event capture

Unikraft / QEMU machine

Execute native products inside a small guest with fresh RAM and fixture-only inputs.

  • Real native machine code
  • Strong clean-boot and host isolation story
  • Good for C, parsers, state machines, storage cores
  • Semantic replay, not instruction replay

Syscall-controlled Linux

Run unmodified x86-64 binaries behind an application kernel or broker that controls the high-value nondeterministic syscalls.

  • Broader compatibility
  • Can control time, RNG, metadata, signals, scheduling
  • Hermit and gVisor demonstrate pieces of the model
  • Large compatibility tail; not the first milestone

Snapshot microVM cluster

Start conventional services from identical snapshots while LD controls the network, disks, workloads, and injected faults.

  • Works with real multi-process systems
  • Cheap resets and parallel timelines
  • Replay is seed/event based and may be statistical
  • Highest near-term operational burden

Preserve LD's architecture

The runtime is a selectable gate, not a new control plane

The six-word ABI stays frozen. RUN-GATES selects a host-configured execution profile. Planner, critic, artifacts, claims, and receipts remain intact.

The highest-leverage constraint

LD writes new software. Prefer products whose core is an explicit transition function: new state + effects = step(old state, event). Clocks, randomness, packets, disk completion, and process failure become input events. This is far cheaper than forcing arbitrary ambient software to become deterministic after the fact.

Sequence

Build value before machinery

Each phase should stand alone as a useful optional LD mode. Do not gate value on completing the entire ladder.

Standardize semantic receipts

Artifact hash, profile, fixture, seed, fault ledger, semantic events, final state hash, and claim results.

Now

Ship the Unikraft profile

Productize the working KV gate as native deterministic-validation mode; add more generated product shapes.

Near term

Add WASI as the default profile

Virtual clock/RNG/files, deterministic fuel, canonical outputs, explicit capabilities, snapshots.

Highest ROI

Add a seeded scenario engine

Generate workloads and controlled faults; shrink failures; run many seeds; preserve every decision in the ledger.

Core moat

Explore compatibility profiles

Only after demand: syscall-controlled Linux for existing binaries and snapshot microVMs for clusters.

Decision

What to build—and what not to promise

Build this

  • A ladder of runtime profiles
  • Deterministic capability manifests
  • Seeded scenario and fault exploration
  • Semantic receipts and state hashes
  • Replay recipes with reproduction rates
  • WASI first, Unikraft for native code

Do not require this yet

  • Instruction-for-instruction replay
  • Deterministic multicore Linux
  • Transparent compatibility with every workload
  • Whole-machine timeline branching
  • A replacement for LD's existing control plane
  • A universal claim of “fully deterministic”
Product language: “Controlled semantic execution with seeded replay.” It is honest, useful, and expandable toward stronger determinism where the economics justify it.
