03 / THE DETERMINISTIC CRITIC

General does not have to mean generative.

The critic does not know how to build your application. It knows the semantics of the plan language and receives the task's policy as data.

That is the same reason a compiler type-checker can validate programs it has never seen. The rules are fixed; the program, artifact set, allowed paths, effects, and typed catalog are inputs.

“But how can deterministic rules work for arbitrary software?”

They do not prove the application is correct. They prove the proposed effects are well-formed and authorized. Application correctness comes later from the task-specific executable contract. Policy and outcome are deliberately different checks.

04 / WHAT BEAM DOES

The runtime is the product boundary.

BEAM is not the planner. It owns the parts that should survive an unreliable planner: supervision, bounded retries, timers, critic service, VM execution, gate processes, ledgers, and—when benchmarking—leased obligations.

07 / THE ONE-SHOT OBJECTION

Yes, the model still generates the solution.

Living Dictionary does not replace model intelligence. On an easy task, a strong model may emit the right files in one shot—and the control program can look thin.

What the architecture adds
  • No mutation before whole-plan validation
  • Explicit, bounded capability order
  • Independent completion evidence
  • Replayable state and failure provenance
  • A typed path for demonstrated reuse
What it does not magically add
  • A proof that generated application logic is correct
  • Guaranteed benefit on trivial one-shot tasks
  • Measured dictionary lift before the new campaign
  • Zero stochastic variance or provider latency
  • Equal maturity across every runtime body
THE TESTABLE CLAIM

Not “Forth writes better code.” The claim is that separating proposal, authorization, execution, and judgment can preserve correctness with fewer model-in-the-loop actions—and leave stronger evidence when something fails.
